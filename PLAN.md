# Веб-приложение «Заявки · База знаний · Оборудование» — техническое задание

Версия 5, финальная: все продуктовые решения согласованы, документ готов к передаче агентам-разработчикам. Подтверждено: при смене здания заявки админом USER-исполнитель из другого здания сбрасывается, ADMIN-исполнитель сохраняется; здания «убираются» из работы деактивацией (`is_active`), удаление — только для неиспользуемых; cookie выбора здания на 30 дней; публичный экран «Все здания» — только чтение.

## 1. Контекст и цель

Единое внутреннее веб-приложение с тремя направлениями и сквозной авторизацией:

- **Заявки** — дашборд по статусам, приём заявок от сотрудников и анонимных посетителей, привязка к зданию, назначение исполнителей, комментарии с медиа, push-уведомления, печать в Word.
- **База знаний** — дерево статей с неограниченной вложенностью и ручной сортировкой, редактируемое всеми авторизованными, закрытые корневые разделы.
- **Учёт оборудования** — здания → склады/кабинеты → оборудование, одиночные и массовые перемещения, журнал, ведомость помещения в Excel с подписями.
- **Авторизация** (`USER`, `ADMIN`, `anonymous`), **Admin-панель**, **статистика по сотрудникам с Excel**, **корзина**.

Успех: посетитель выбирает здание и сразу видит его заявки, создаёт новую и получает бессрочную ссылку на карточку; сотрудник ведёт заявки своего здания и получает push о новых заявках в нём; база знаний наполняется инструкциями с фото и видео между абзацами; оборудование перемещается одиночно и массово с историей; ведомость помещения печатается из Excel; админ настраивает справочники, календарь, часовой пояс, здания и роли; каждый сотрудник видит свою статистику и выгружает Excel; заявка печатается в Word; `docs/HANDOVER.md` позволяет другому ИИ-агенту продолжить работу без контекста чата.

**Стек (согласован):** Back — Go + MySQL 8; Front — React + TypeScript; медиа — локальный диск с выдачей через API под проверкой прав; push — браузерный Web Push.

## 2. Объём

### Входит
- Аутентификация (логин/пароль, JWT access + refresh cookie), роли, блокировка, смена своего пароля.
- Admin-панель: пользователи с обязательным зданием; справочники (виды проблем, типы оборудования); настройки (имя приложения, срок дедлайна, маска рабочих дней, праздники, часовой пояс, время напоминаний, вкл/выкл push, названия/цвета статусов); здания (с активностью) и склады; видимость разделов БЗ; корзина.
- Заявки: создание (в т.ч. анонимно), обязательное здание, дашборд по 4 статусам, карточка, дедлайн по рабочему календарю, исполнитель, комментарии с вложениями, доступ анонима по токен-ссылке, экспорт в Word, смена здания админом.
- Публичный периметр: страница выбора здания со счётчиками, дашборд здания `/b/{id}`, сводный обзор «Все здания», cookie на 30 дней, переключатель зданий.
- Ограничение видимости заявок по зданию сотрудника; фильтр по зданию виден всем, у USER заблокирован на своём здании.
- База знаний: дерево с неограниченной вложенностью и drag-n-drop сортировкой, статьи с медиа внутри текста, скрытые корневые разделы.
- Оборудование: здания, склады/кабинеты, единицы, одиночные и массовые перемещения, журнал, ведомость помещения в Excel с местами для подписей.
- Push-уведомления: браузерные подписки, адресация по зданию, ежедневные напоминания о дедлайне.
- Статистика: личная и сводная по сотрудникам с фильтром по зданию, выгрузка в Excel.
- Docker-развёртывание, сидинг демо-данных, автотесты, OpenAPI-контракт, `docs/HANDOVER.md`.

### Сознательно не входит
- Самостоятельная регистрация (аккаунты создаёт только ADMIN).
- Email/SMS/Telegram-уведомления (только Web Push).
- Импорт/экспорт в 1С, SSO/LDAP, интеграции с внешними системами.
- Мобильные приложения, PWA-офлайн-режим.
- История версий статей/заявок, полный аудит-лог (кроме журнала перемещений).
- Мультиарендность, мультиязычность, антивирусная проверка загрузок, S3/CDN.
- Печать PDF (только Word и Excel), Word-акт ведомости, логотипы и реквизиты в документах, публичные рейтинги сотрудников.

## 3. Требования

### 3.1 Роли, здания и матрица прав

Роли: `anonymous`, `USER`, `ADMIN`. Аккаунты создаёт только ADMIN. У `USER` ровно одно здание (`users.building_id`, обязательно при создании и при смене роли на USER), у `ADMIN` закрепления нет. Заблокированный аккаунт получает `401`, refresh-токены отзываются.

Ограничение по зданию действует **только на заявки**; база знаний и оборудование доступны всем авторизованным (иначе невозможны перемещения между зданиями).

| Действие | anonymous | USER | ADMIN |
|---|---|---|---|
| Страница выбора здания (`/`) | да | редирект на `/tickets` | редирект на `/tickets` |
| Публичный дашборд здания `/b/{id}` (3 статуса) | да | — | — |
| Сводный обзор «Все здания» (публичный, только чтение) | да | — | — |
| Список заявок | — | только своего здания | все здания |
| Фильтр по зданию | через выбор здания | есть, но заблокирован на своём здании | любой, включая «Все здания» |
| Карточка/комментарии/Word заявки | только своей по токену | только своего здания | любого здания |
| Создание заявки (со зданием) | да | да (здание = своё) | да (любое здание) |
| Смена здания заявки | — | нет | да, с проверкой исполнителя |
| Смена статуса | — | заявки своего здания | любой |
| Назначение исполнителя | — | только себя, заявка своего здания | USER из здания заявки или ADMIN |
| Изменение дедлайна | — | нет | да |
| Правка полей заявки | — | только если исполнитель = он | да |
| Удаление в корзину | — | нет | да |
| БЗ: чтение публичных разделов | да | да | да |
| БЗ: чтение скрытых разделов | нет (404) | да | да |
| БЗ: создание/правка/сортировка | нет | да | да |
| БЗ: удаление, тумблер видимости | нет | нет | да |
| Оборудование: чтение/создание/правка/перемещение (в т.ч. массовое) | нет | да | да |
| Оборудование: удаление | нет | нет | да |
| Ведомость помещения (Excel) | нет | да | да |
| Здания/склады: чтение | публично только названия и счётчики | да | да |
| Здания/склады: запись, деактивация | нет | нет | да |
| Пользователи, справочники, настройки, корзина, сводная статистика | нет | нет (403) | да |
| Личная статистика + Excel | нет | своя | своя и любая (фильтр по зданию) |
| Push-подписка | нет (нет аккаунта) | своя | своя |

### 3.2 Аутентификация и аккаунты (AUTH)

- `AUTH-1` Вход по `login` + `password`; пароль — argon2id (memory 64 МБ, iterations 3, parallelism 1); неверные данные → `401 INVALID_CREDENTIALS` без раскрытия существования логина.
- `AUTH-2` Access-токен JWT HS256 (TTL 15 мин) в `Authorization: Bearer`; refresh — httpOnly `SameSite=Lax` cookie на `/api/auth`, TTL 7 дней, хранится SHA-256 хешем, ротация при каждом refresh, повторное использование старого → `401` + отзыв цепочки.
- `AUTH-3` Rate limit: 10 неудачных входов на пару `login+IP` за 10 минут → `429` + `Retry-After`; публичное создание заявки — 5 запросов / 10 минут на IP; публичные справочники зданий — 120 запросов / 10 минут на IP.
- `AUTH-4` ADMIN создаёт пользователя (логин, ФИО, роль, временный пароль ≥8 символов); для `USER` обязателен `building_id` (`422 BUILDING_REQUIRED_FOR_USER`), в форме поле обязательно и не может быть пустым; `must_change_password=true`; до смены пароля все эндпоинты кроме `GET /api/auth/me`, `POST /api/auth/password`, `POST /api/auth/logout` → `428 PASSWORD_CHANGE_REQUIRED`.
- `AUTH-5` Пользователь меняет свой пароль (`current_password` + новый ≥8 символов); ADMIN сбрасывает пароль любому без текущего (флаг `must_change_password`).
- `AUTH-6` Каждый авторизованный запрос проверяет `is_active` в БД; блокировка действует не позднее следующего запроса.
- `AUTH-7` Запрет самоблокировки и понижения последнего активного ADMIN → `409 CANNOT_MODIFY_SELF` / `409 LAST_ADMIN`.
- `AUTH-8` Смена роли `ADMIN→USER` требует указания здания (`422`); `USER→ADMIN` очищает `building_id`; перевод сотрудника в неактивное здание запрещён (`422 BUILDING_INACTIVE`).
- `AUTH-9` Пользователь без здания (аномалия данных) получает от API заявок `409 BUILDING_NOT_ASSIGNED`, UI показывает баннер «Здание не назначено, обратитесь к администратору».

### 3.3 Заявки (TICKET)

- `TICKET-1` Статусы фиксированы кодами `new`, `in_progress`, `deferred`, `done`; названия и цвета настраиваются; API отдаёт `status`, `status_label`, `status_color`.
- `TICKET-2` Поля: `building_id` (обязательное), `applicant_name` (1–120), `cabinet` (1–32, текст), `problem_type_id` (обязателен), `description` (1–5000), `deadline` (DATE), `executor_id` (nullable), `status`, `completed_at`, `created_at`, `access_token` (только анонимная заявка, выдаётся один раз).
- `TICKET-3` Дедлайн считается на сервере в `timezone`: к дате создания прибавляется `N` **рабочих** дней (`deadline_days`, по умолчанию 2, 1–30) по календарю `CAL-1`. Пример: пятница + 2 при Пн–Сб → вторник. Изменение настроек не пересчитывает существующие дедлайны.
- `TICKET-4` Аноним создаёт заявку с обязательным зданием: без `building_id` → `422 VALIDATION_ERROR`; неактивное/несуществующее здание → `404`.
- `TICKET-5` Публичный дашборд здания: группировка по `new`, `in_progress`, `deferred`, `done` отсутствует полностью; поля карточки: `id`, `building_name`, `applicant_name`, `cabinet`, `problem_type_name`, `status`, `status_label`, `deadline`, `executor_name`, `created_at`. Без `building_id` тот же эндпоинт отдаёт сводку по всем активным зданиям (экран «Все здания»); `description`, комментарии и файлы не отдаются никогда.
- `TICKET-6` Страница выбора здания: `GET /api/public/buildings` возвращает только активные здания с названием и счётчиками `new`, `in_progress`, `deferred`; завершённые не учитываются; склады и пользователи не отдаются.
- `TICKET-7` Видимость для USER: список, карточка, комментарии, Word и «назначить себя» — только заявки своего `building_id`; заявка другого здания → `404` (существование не раскрывается). ADMIN видит все заявки, фильтр по зданию с вариантом «Все здания» (по умолчанию).
- `TICKET-8` Исполнитель по умолчанию пуст. USER назначает только себя, в том числе перехватывает заявку своего здания у другого исполнителя; `executor_id ≠ self` → `403 ASSIGN_OTHER_USER`. ADMIN назначает активного USER из здания заявки или любого ADMIN; USER из другого здания → `422 EXECUTOR_WRONG_BUILDING`; ADMIN снимает исполнителя.
- `TICKET-9` Дедлайн меняет только ADMIN (`YYYY-MM-DD`, дата в прошлом допустима). Здание меняет только ADMIN: если назначенный USER-исполнитель принадлежит другому зданию, исполнитель сбрасывается в `null`, ответ содержит `executor_reset: true`; ADMIN-исполнитель сохраняется; UI предупреждает о сбросе до сохранения.
- `TICKET-10` Статус меняет USER (только своего здания) и ADMIN (любой); при `done` проставляется `completed_at`, при выходе из `done` — обнуляется.
- `TICKET-11` USER правит `applicant_name`, `cabinet`, `problem_type_id`, `description` только будучи исполнителем заявки своего здания, иначе `403 NOT_EXECUTOR`/`404`; ADMIN — всегда.
- `TICKET-12` Удаление — только ADMIN, в корзину (`deleted_at`); восстановление и окончательное удаление — по `TRASH-*`.
- `TICKET-13` Аноним при создании получает `access_token` (32 случайных байта base64url, в БД SHA-256) и URL `/t/{token}`; по нему доступны карточка, комментарии, вложения и Word-экспорт только этой заявки; чужой/битый токен → `404`; токен бессрочный.
- `TICKET-14` Комментарий: текст до 3000 символов (может быть пустым при наличии вложения), автор (пользователь или имя анонима), до 5 вложений; список плоский, по 50 на страницу.
- `TICKET-15` Авторизованный список: фильтры статус (мультивыбор), исполнитель, вид проблемы, здание (у USER заблокирован на своём), диапазон дат, поиск по `applicant_name`/`cabinet`; сортировка по `created_at`/`deadline`; серверная пагинация (`size` ≤ 100) с `total`.
- `TICKET-16` Сервер отдаёт флаг `is_overdue` (расчёт по `timezone` и дедлайну); клиент только отображает.

### 3.4 Рабочий календарь, часовой пояс и дедлайны (CAL)

- `CAL-1` Настройки: `workdays` — маска дней недели, по умолчанию Пн–Сб; `holidays` — список исключаемых дат; редактируются в Admin-панели.
- `CAL-2` `timezone` — часовой пояс приложения, по умолчанию `Asia/Yekaterinburg` (UTC+5); валидируется как IANA-идентификатор (`422` при неизвестном). Определяет границы суток для дедлайнов, «сегодня/просрочено», время джоб и форматирование дат в API и документах.
- `CAL-3` `deadline_reminder_time` — время ежедневных напоминаний, по умолчанию `10:00`, формат `HH:MM`, 00:00–23:59, интерпретируется в `timezone`.
- `CAL-4` Рабочий день = день из маски, отсутствующий в `holidays`; отсчёт `N` рабочих дней начинается со следующего календарного дня после даты создания (по `timezone`).
- `CAL-5` Изменение календаря/пояса влияет на новые заявки и подсчёт просрочки; существующие дедлайны не пересчитываются.
- `CAL-6` Unit-тесты: пятница+2 при Пн–Сб → вторник; четверг+2 при Пн–Пт с праздником в пятницу → понедельник; заявка, созданная в 23:50 по Екатеринбургу, относится к текущим суткам этого пояса.

### 3.5 База знаний (KB)

- `KB-1` Узел: `title` (1–200), `content_html` (0–100 000), `parent_id` (nullable), `sort_order`, `is_hidden_for_anon` (только у корневых, у потомков наследуется).
- `KB-2` Вложенность не ограничена; цикл → `409 CYCLE_DETECTED`; родитель удалён → `400`; UI отображает глубину ≥ 5.
- `KB-3` Создание/правка/сортировка — любой авторизованный; удаление — только ADMIN, каскадно с поддеревом (в корзину), ответ содержит число потомков.
- `KB-4` `content_html` санитизируется (bluemonday, allowlist: заголовки, списки, ссылки http/https, `<img>`, `<video>/<source>`, code/pre, таблицы); `<script>`, `on*`, `iframe` удаляются.
- `KB-5` Медиа между абзацами: `<img src="/api/files/{id}">`, `<video><source src="/api/files/{id}"></video>`; проверка существования файлов со `scope=kb`, иначе `400 INVALID_MEDIA_REF`.
- `KB-6` Ручная сортировка: `PATCH /api/kb/nodes/{id}` с `parent_id`/`sort_order` и `POST /api/kb/nodes/{id}/move` `{parent_id, before_node_id?}`; переиндексация с шагом 10; drag-n-drop с оптимистичным обновлением и откатом.
- `KB-7` Аноним видит только публичные корневые разделы и потомков; прямой запрос скрытого узла → `404`; тумблер видимости — только ADMIN.
- `KB-8` Дерево отдаётся одним запросом (`GET /api/kb/tree`), сортировка `sort_order, title`.

### 3.6 Оборудование (EQ)

- `EQ-1` `building` (1) → `warehouse` (N); у здания `name`, необязательный `address`, `is_active`; склад/кабинет — одна сущность `warehouse` (`name`), имя уникально в рамках здания. Неактивное здание не показывается анонимам и не предлагается при создании заявки и закреплении сотрудника, но остаётся в истории и фильтрах.
- `EQ-2` Оборудование: `name` (1–200), `equipment_type_id`, `serial_number` (1–100), `registration_number` (1–100, уникален среди неудалённых → `409 DUPLICATE_REGISTRATION_NUMBER`), `warehouse_id` (обязателен), `deleted_at`.
- `EQ-3` Перемещение `POST /api/equipment/{id}/move` `{to_warehouse_id, comment?}` в транзакции с `SELECT ... FOR UPDATE`: обновление склада + запись журнала (`from_warehouse_id`, `to_warehouse_id`, `moved_by_user_id`, `moved_at`, `comment`); в тот же склад → `409 SAME_WAREHOUSE`. Перемещение внутри неактивного здания разрешено только ADMIN (`422 BUILDING_INACTIVE` для USER).
- `EQ-4` Массовое перемещение `POST /api/equipment/bulk-move` `{equipment_ids[1..200], to_warehouse_id, comment?}`: одна транзакция, блокировки по возрастанию id, журнал по каждой единице; несуществующий id → `404` с откатом; >200 → `422`.
- `EQ-5` Журнал неизменяем (нет PATCH/DELETE), отдаётся с именами складов/зданий/пользователя, `ORDER BY moved_at DESC`, пагинация.
- `EQ-6` «Удаление» задействованного здания — только деактивация (`is_active=false`): здание исчезает из публичного выбора, из формы заявки и из выбора при создании пользователя; история сохраняется. Физическое удаление разрешено, только если нет складов, оборудования, закреплённых пользователей и заявок; иначе `409 BUILDING_IN_USE`. Удаление склада с оборудованием → `409 WAREHOUSE_NOT_EMPTY`; удаление оборудования — только ADMIN, в корзину.
- `EQ-7` Списки с фильтрами по зданию/складу/типу и поиском по названию/серийному/регистрационному номеру, серверная пагинация; чтение — все авторизованные, без ограничения по зданию.
- `EQ-8` Ведомость помещения (Excel): `GET /api/warehouses/{id}/inventory.xlsx` — шапка (название приложения, здание, помещение, дата формирования, всего единиц), таблица (`№`, наименование, тип, серийный номер, регистрационный номер, примечание), блок подписей «Передал: ФИО ______ должность ______ подпись ______ дата ______», «Принял: ФИО ______ должность ______ подпись ______ дата ______», строка «М.П.». До 1000 позиций, свыше → `422`.

### 3.7 Уведомления (NOTIF)

- `NOTIF-1` Канал — браузерный Web Push (VAPID, HTTPS; на `localhost` без TLS). Подписка: `user_id`, `endpoint` (unique), `p256dh`, `auth`, `user_agent`, `created_at`, `last_success_at`, `is_active`. Получают только `USER` и `ADMIN`.
- `NOTIF-2` Адресация:
  - `NEW_TICKET` — активные USER с `building_id` = здание заявки + все активные ADMIN, кроме автора; если за зданием никто не закреплён — только ADMIN;
  - `TICKET_ASSIGNED` — назначенному исполнителю;
  - `NEW_COMMENT` — исполнителю и автору-сотруднику заявки, кроме автора комментария;
  - `DEADLINE_TODAY`/`DEADLINE_OVERDUE` — исполнителю (если есть) и всем ADMIN, ежедневно в `deadline_reminder_time` по `timezone`, не более одного уведомления каждого типа на заявку в сутки.
- `NOTIF-3` Доставка через outbox: событие в таблицу, воркер опрашивает раз в 30 секунд, до 3 попыток с экспоненциальной задержкой; `404/410` → подписка `is_active=false`; результат в лог с `request_id`.
- `NOTIF-4` Payload: `title` (≤60), `body` (≤120), `url` (deep link на карточку), `tag` (схлопывание), `icon`; клик открывает/фокусирует вкладку.
- `NOTIF-5` Пользователь включает/выключает push на устройстве; запрос разрешения — только по явному действию; UI показывает состояние подписки.
- `NOTIF-6` Глобальный `push_enabled` в настройках; при `false` события в outbox не создаются.
- `NOTIF-7` Идемпотентность напоминаний по ключу `event_type + ticket_id + local_date`; смена пояса/времени применяется к следующему запуску.

### 3.8 Статистика (STATS)

- `STATS-1` `GET /api/stats/me?from&to` (USER/ADMIN) и `GET /api/admin/stats?user_id&building_id&from&to` (ADMIN). Метрики: `total_done`, `done_in_period`, `avg_resolution_hours`, `median_resolution_hours`, `on_time_percent`, `overdue_count`, `by_problem_type[]`, `by_month[]`.
- `STATS-2` Учитываются заявки с `completed_at`; время выполнения в часах с округлением до 0.1; «в срок» — `completed_at ≤ deadline`; корзина исключается; период по `completed_at` в `timezone`; личная статистика не ограничена зданием.
- `STATS-3` Excel `GET /api/stats/export.xlsx?user_id&building_id&from&to`: лист «Сводка» (ФИО, логин, период, метрики), лист «Заявки» (id, здание, создана, завершена, дедлайн, в срок/просрочено, вид проблемы, кабинет, заявитель); имя `stat_{login}_{from}_{to}.xlsx`; свой отчёт — всем, чужой — только ADMIN.
- `STATS-4` `/profile`: метрики, смена пароля, push-переключатель, отображение своего здания.

### 3.9 Документы и печать (DOC)

- `DOC-1` Word-заявка: `GET /api/tickets/{id}/export.docx` (USER — своё здание, ADMIN — любое) и `GET /api/public/tickets/{token}/export.docx` (аноним по своему токену). Генерация по шаблону `backend/templates/ticket.docx`, плейсхолдеры: `{{app_name}}`, `{{ticket_id}}`, `{{building}}`, `{{created_at}}`, `{{applicant_name}}`, `{{cabinet}}`, `{{problem_type}}`, `{{deadline}}`, `{{status}}`, `{{executor}}`, `{{description}}`, `{{comments}}` (дата, автор, текст, вложения), `{{generated_at}}`; форматирование шаблона сохраняется; логотип и реквизиты не добавляются; имя `ticket_{id}.docx`.
- `DOC-2` Excel-статистика — `STATS-3`; ведомость помещения — `EQ-8` (только Excel).
- `DOC-3` Выгрузки: корректные `Content-Type`, `Content-Disposition: attachment`, `Cache-Control: no-store`; формируются только на сервере, с тестами содержимого.
- `DOC-4` Шаблоны и плейсхолдеры — в `docs/templates.md`; даты в `timezone`.

### 3.10 Корзина и восстановление (TRASH)

- `TRASH-1` `GET /api/admin/trash?type=ticket|kb|equipment&page` — дата удаления, кто удалил, краткое описание.
- `TRASH-2` `POST /api/admin/trash/{type}/{id}/restore`: заявка возвращается со статусом и зданием (и `completed_at`, если была завершена); если здание деактивировано — восстановление разрешено с предупреждением; узел БЗ — только при живом родителе или `parent_id=null`; оборудование — при живом складе; конфликт регистрационного номера → `409`.
- `TRASH-3` `DELETE /api/admin/trash/{type}/{id}` — физическое удаление с комментариями и файлами, необратимо, с подтверждением в UI.
- `TRASH-4` Автоочистка старше 90 дней — ежедневной джобой в `timezone`, с логом.
- `TRASH-5` Восстановление узла не восстанавливает потомков — UI предупреждает.

### 3.11 Публичный периметр (PUB)

- `PUB-1` Корень `/`: для неавторизованного — страница выбора здания с карточками активных зданий и счётчиками `new`/`in_progress`/`deferred`. При наличии cookie `anon_building_id` и активном здании — сразу редирект на `/b/{id}`; ссылка «Сменить здание» возвращает на выбор.
- `PUB-2` `/b/{buildingId}` — публичный дашборд здания: 3 колонки по статусам, карточки с ограниченными полями, кнопка «Создать заявку»; несуществующее или неактивное здание → 404-страница.
- `PUB-3` Cookie `anon_building_id` (SameSite=Lax, path=/, срок 30 дней, доступна JS) обновляется при выборе здания и при создании заявки с другим зданием; после создания — переход на дашборд выбранного здания.
- `PUB-4` Быстрый переключатель зданий в шапке дашборда (активные здания + «Все здания»). Режим «Все здания» — сводный обзор трёх колонок по всем зданиям, только чтение: кнопка создания неактивна с подсказкой «Выберите здание для создания заявки».
- `PUB-5` Форма создания: здание подставлено из выбранного и может быть изменено; после успеха — экран со ссылкой `/t/{token}` и кнопкой копирования.
- `PUB-6` Карточка `/t/{token}`: поля заявки, здание, комментарии, вложения (просмотр/воспроизведение), добавление комментария с файлами, «Скачать в Word».
- `PUB-7` Публичная БЗ доступна независимо от выбранного здания.

### 3.12 Нефункциональные требования (NFR)

- `NFR-1` На 10 000 заявок в 10 зданиях, 2 000 единиц оборудования, 500 узлов БЗ: p95 списочных ответов ≤ 300 мс, одиночных ≤ 150 мс при 50 RPS; Excel/Word ≤ 2 с на 1000 строк.
- `NFR-2` Безопасность: HTTPS на reverse proxy (обязательно для Web Push), CORS только с разрешённого origin, параметризованные запросы, JWT-секрет из env ≥32 симв., запрет утечки чужих заявок (`404` вместо `403`), публичные эндпоинты не отдают `description` и внутренние сущности.
- `NFR-3` Совместимость: последние 2 версии Chrome, Firefox, Safari, Edge; адаптив от 375 px; push в Chrome/Firefox/Edge/Safari ≥16.4, иначе пояснение в UI.
- `NFR-4` Наблюдаемость: JSON-логи с `request_id`, `user_id`, `route`, `status`, `duration_ms`; `/health`, `/health/ready`; счётчики outbox в логах воркера.
- `NFR-5` Данные: миграции только вперёд, идемпотентный сидинг, ежедневный бэкап MySQL и uploads (`deploy/backup.sh`).
- `NFR-6` Качество: golangci-lint без ошибок, покрытие доменных пакетов ≥70%; фронт — `tsc --noEmit` и ESLint без ошибок, Vitest ≥60%.
- `NFR-7` Время: все серверные расчёты «сегодня», дедлайнов и джоб — в `timezone`; клиент не вычисляет дедлайн и просрочку.
- `NFR-8` Cookie выбора здания не содержит персональных данных и не даёт доступа к закрытым данным: сервер всегда проверяет здание заново.

## 4. Ограничения и допущения

1. **MySQL 8.4**, один инстанс API; дерево БЗ через recursive CTE.
2. **Медиа на локальном диске** (`/data/uploads`), выдача через API под проверкой прав; S3/CDN нет.
3. **Дедлайн** — `N` рабочих дней (`N`=2 по умолчанию) по календарю Пн–Сб с праздниками; существующие дедлайны не пересчитываются.
4. **Часовой пояс** — `Asia/Yekaterinburg` (UTC+5) по умолчанию, настраивается; напоминания в 10:00 по этому поясу, настраиваются; DST не применяется.
5. **Статусы** — 4 фиксированных кода; редактируются названия и цвета.
6. **Аккаунты** создаёт только ADMIN; первичный ADMIN — сидингом из env; для USER здание обязательно (API и UI).
7. **Одно здание у USER**; у ADMIN закрепления нет, по умолчанию «Все здания». Ограничение по зданию — только заявки; БЗ и оборудование доступны всем авторизованным.
8. **Здания не удаляются, а деактивируются** (`is_active=false`); неактивное здание скрыто из публичного выбора, формы заявки и выбора здания для пользователя, история сохраняется. Физическое удаление — только для зданий без складов, оборудования, пользователей и заявок.
9. **Смена здания заявки** — только ADMIN; USER-исполнитель из другого здания сбрасывается (`executor_reset: true`), ADMIN-исполнитель сохраняется.
10. **Аноним**: выбор здания через `/`, cookie `anon_building_id` 30 дней, дашборд `/b/{id}`, переключатель и сводка «Все здания» (только чтение); карточка — только по своему токену.
11. **Удаление** заявок, узлов БЗ и оборудования — в корзину, 90 дней, затем автоочистка; узлы БЗ восстанавливаются без потомков.
12. **Права на оборудование:** чтение/создание/правка/перемещение/массовое перемещение — все авторизованные; удаление, здания и склады — ADMIN.
13. **Оборудование всегда привязано к складу**; состояния «не размещено» нет.
14. **Push** — только браузерный Web Push, без email/SMS; напоминания ежедневно в настраиваемое время.
15. **Статистика**: своя — каждому, сводная — только ADMIN; рейтингов нет.
16. **Word-заявка** — серверный `.docx` без логотипа и реквизитов; PDF нет.
17. **Ведомость помещения** — только `.xlsx` с подписями «Передал/Принял» и «М.П.».
18. **Front:** React 19 + TS strict, Vite, Ant Design 5, React Router, TanStack Query, react-hook-form, TipTap (inline media), dnd-kit, Vitest + RTL + MSW, Playwright.
19. **Back:** Go 1.23+, chi, sqlc/явный SQL, golang-migrate, golang-jwt/v5, argon2id, `log/slog`, `webpush-go`, `excelize`, шаблонный docx-генератор, `time.LoadLocation`.
20. Один репозиторий: `backend/`, `frontend/`, `openapi/`, `docs/`, `deploy/`.
21. Развёртывание — `docker compose` (MySQL + api + nginx), TLS на внешнем reverse proxy (обязательно для push).
22. **`docs/HANDOVER.md`** создаётся финальным блоком по структуре §9; аналитик (этот чат) файлы не создаёт — ТЗ и шаблон отчёта передаются текстом.

## 6. Блоки разработки

### 6.1 Back (Go + MySQL)

**Б1. Фундамент, контракт, ядро аутентификации** — волна 1, агент 1.
Что меняется: `go.mod`, `cmd/api`, конфиг из env, MySQL, `golang-migrate` + `0001_core` (users, refresh_tokens, settings с `timezone=Asia/Yekaterinburg`, `workdays`, `deadline_reminder_time=10:00`, problem_types, equipment_types, buildings(id,name,address,is_active,created_at), holidays; сидинг админа), полный `openapi/openapi.yaml` (заглушки `501`), middleware (request_id, recover, CORS, slog, rate limit), login/refresh/logout/me, `requireAuth`/`requireRole`, интерфейсы `Calendar` и `Notifier`, формат ошибок, `/health`, `/health/ready`, Swagger UI `/docs`, `docker-compose.yml`, `Dockerfile`, `Makefile`.
Зависимости: нет.
Критерии: стек поднимается; миграции идемпотентны; логин → 200 + refresh-cookie; неверный пароль → 401; `/api/auth/me` без токена → 401; USER на админском маршруте → 403; `openapi.yaml` проходит redocly lint + schemathesis smoke; `/health/ready` → 503 без БД.

**Б2. Пользователи, роли, пароли, здание пользователя** — волна 2, агент 1.
Что меняется: `internal/users`, миграция `0002_users_*` (`users.building_id` FK ON DELETE RESTRICT), `GET/POST /api/admin/users`, `PATCH /api/admin/users/{id}`, `POST /api/admin/users/{id}/password`, `GET /api/users/assignable?ticket_id=`, `POST /api/auth/password`; правила `AUTH-4`–`AUTH-9`.
Зависимости: Б1.
Критерии: USER без здания → 422; перевод в неактивное здание → 422 `BUILDING_INACTIVE`; `ADMIN→USER` без здания → 422, `USER→ADMIN` очищает здание; временный пароль даёт `428` на прочих эндпоинтах; блокировка → 401 со следующего запроса; самоблокировка/последний ADMIN → 409; USER на `/api/admin/users` → 403; `assignable` для заявки здания A отдаёт только USER здания A + ADMIN.

**Б3. Файлы и медиа** — волна 2, агент 2.
Что меняется: `internal/files` (стриминг, magic bytes, лимиты 10 МБ фото / 200 МБ видео, sha256, диск, метаданные, `comment_files`), `POST /api/files`, `GET /api/files/{id}`, `GET /api/public/files/{id}?token=`, Range, фоновая очистка orphan.
Зависимости: Б1.
Критерии: `.exe` под видом jpeg → 415; 11 МБ фото → 413; видео 200 МБ воспроизводится с 206; чужой токен → 403/404; orphan старше суток удаляется; `nosniff` присутствует.

**Б4. Оборудование: здания, склады, единицы, перемещения** — волна 2, агент 3.
Что меняется: `internal/buildings`, `internal/equipment`, миграции `0004_equipment_*` (warehouses, equipment, equipment_movements), CRUD зданий (с `is_active`, деактивация, проверка `BUILDING_IN_USE` по складам/пользователям и маппинг FK-ошибки), CRUD складов, CRUD оборудования, `move`, журнал, `EQ-1`–`EQ-3`, `EQ-5`–`EQ-7`.
Зависимости: Б1.
Критерии: перемещение меняет склад и создаёт 1 запись журнала; 50 параллельных перемещений одной единицы — 50 записей без потерь; дубль регистрационного номера → 409; удаление непустого склада → 409; деактивация здания убирает его из публичного выбора и формы заявки, история доступна; физическое удаление используемого здания → 409; USER не может переместить оборудование в неактивное здание (422), ADMIN может; журнал не редактируется.

**Б5. Заявки, публичные дашборды, здание** — волна 3, агент 1.

## 7. План проверки

**Back**
1. Unit-тесты: рабочие дни (пятница+2 при Пн–Сб; праздник в пятницу при Пн–Пт), границы суток `Asia/Yekaterinburg` (23:50 — те же сутки), права по матрице с зданиями A/B, смена здания с проверкой исполнителя (USER сбрасывается, ADMIN сохраняется), массовое перемещение, медиана/среднее, видимость БЗ, восстановление из корзины.

4. Негативные: MIME-подмена, oversized, битый JWT, чужой токен, заявка чужого здания (404), исполнитель из другого здания (422), дубли номеров, цикл в дереве, 201 id в bulk-move, 1001 позиция, повторный refresh, невалидные `timezone`/`HH:MM`, деактивированное здание в публичном API (404), перевод сотрудника в неактивное здание (422).

8. Ручные: бэкап/восстановление, ротация refresh, блокировка в сессии, автоочистка корзины и orphan, запуск джобы в 10:00 по Екатеринбургу, деактивация здания и его исчезновение из публичного выбора и формы заявки.

**Front**

3. Playwright e2e (13 сценариев из Ф11) против полного стека.
4. Ручные: приватное окно (выбор здания → заявка → ссылка → Word), 375 px, клавиатурная навигация, 403/404/409/500, разрешения push в Chrome/Firefox/Safari.
5. Метрики: 0 ошибок TS/ESLint, axe без critical, Lighthouse ≥90, бандл ≤600 КБ gzip.
