# Architecture Decision Records (ADR)

Краткие записи о значимых решениях. Формат: контекст → решение → последствия.
Новые решения добавляются в конец; изменённые помечаются «заменено ADR-N».

## ADR-1. MySQL 8 как единственное хранилище

**Контекст.** Внутреннее приложение на 12 сотрудников, 50–10 000 заявок; нужны
транзакции, FK и простой бэкап.
**Решение.** MySQL 8.4 (`utf8mb4_0900_ai_ci`, `default-time-zone=+00:00`), без
отдельного кэша/очереди. Outbox-таблица в MySQL вместо Redis/RabbitMQ.
**Последствия.** Один бэкап (`mysqldump`), одна точка откачки; при росте нагрузки
на чтение — реплика/кэш, outbox уже отделяет push от запроса.

## ADR-2. UTC в БД, часовой пояс — в настройках приложения

**Контекст.** Пользователи в одном поясе, но пояс админ меняет; дедлайны —
календарные даты.
**Решение.** Все `DATETIME` — UTC; `DATE` — календарная дата без пояса; пояс
приложения (`settings.timezone`, дефолт `Asia/Yekaterinburg`) применяется в Go
через `platform.Calendar`. MySQL tz-таблицы и `CONVERT_TZ` не используются.
**Последствия.** Нет зависимости от `mysql_tzinfo_to_sql`; смена пояса
применяется сразу (атомарный `CalendarProvider`), но исторические «календарные»
сравнения трактуются в текущем поясе — это осознанно (CAL-2).

## ADR-3. Рабочий календарь считается на сервере

**Контекст.** Дедлайн — N рабочих дней с учётом Пн–Сб и праздников.
**Решение.** `platform.Calendar` (`WorkingDays`, `Today`, `FormatDate`) + маска
`workdays` и таблица `holidays`; дедлайн при создании/переносе ставит сервер.
Клиент даты не пересчитывает.
**Последствия.** Один источник истины; тесты календаря детерминированы
(`FixedClock`). Праздники, добавленные после создания заявки, не пересчитывают
старые дедлайны.

## ADR-4. Здание — ось видимости и публичной навигации

**Контекст.** USER должен видеть только заявки своего здания; аноним — дашборд
выбранного здания.
**Решение.** `users.building_id` (обязателен для USER), `tickets.building_id`
(обязателен); фильтр по зданию принудительно применяется в сервисе, не в
middleware. Публичные `/b/{id}` и cookie выбранного здания на 30 дней.
**Последствия.** БЗ и оборудование общие для всех авторизованных (иначе
невозможны перемещения); здание меняет ADMIN, смена сбрасывает исполнителя.

## ADR-5. Деактивация вместо удаления

**Контекст.** История заявок/оборудования ссылается на здания, склады,
справочники; удаление ломает отчёты.
**Решение.** `is_active=0` для зданий/пользователей/справочников; `deleted_at`
для складов/оборудования/БЗ/заявок (корзина). Физическое удаление — только
пустого склада; FK — `RESTRICT`/`SET NULL`.
**Последствия.** Растёт объём таблиц, зато история и аудит целы; корзина (Б10)
чистит `deleted_at` старше 90 дней.

## ADR-6. Локальный диск для медиа, выдача через API

**Контекст.** Фото до 10 МБ и видео до 200 МБ, проверка прав на каждый файл.
**Решение.** `UPLOAD_DIR/YYYY/MM/{uuid}.{ext}`, метаданные в `files`, выдача
`http.ServeContent` с `Range`/`nosniff` только через API; MIME по сигнатуре,
sha256, лимиты. S3/CDN не используются (PLAN §4).
**Последствия.** Простой бэкап (tar), но диск — единственная точка отказа;
горизонтальное масштабирование API требует общего тома.

## ADR-7. JWT access + refresh-cookie

**Контекст.** SPA и публичный периметр; нужен «выход по истечении» и отзыв
сессий при блокировке.
**Решение.** Access-JWT на 15 минут в памяти фронта; refresh — httpOnly
cookie `path=/api/auth`, 7 дней, ротация при каждом refresh, хеш в БД; при
повторном использовании старого токена цепочка отзывается.
**Последствия.** Нет server-side сессий; блокировка пользователя проверяется на
каждом запросе (`AUTH-6`) и отзывает refresh-токены.

## ADR-8. argon2id и одинаковый ответ на неверный логин/пароль

**Решение.** `golang.org/x/crypto/argon2`, параметры в `auth.HashPassword`;
неверная пара и заблокированный аккаунт → одинаковый `401 INVALID_CREDENTIALS`;
rate limit 10 попыток/10 минут на login+IP (`AUTH-3`).
**Последствия.** Дороже CPU, чем bcrypt; зато нет перебора и раскрытия логинов.

## ADR-9. MIME по сигнатуре, UUID-имена

**Решение.** Первые 512 байт определяют тип; расширение — только для удобства;
имя файла на диске — UUID; исходное имя не используется в пути. Загрузка во
временный staging-файл, затем атомарный `Commit`.
**Последствия.** Нельзя загрузить «.jpg» с исполняемым содержимым под видом
фото; staging-мусор чистится воркером.

## ADR-10. Санитизация HTML и авторизация медиа БЗ

**Контекст.** Статьи БЗ содержат HTML с картинками/видео; аноним видит только
публичные разделы.
**Решение.** `bluemonday` с белым списком тегов/атрибутов; ссылки на медиа
разрешаются отдельным авторизатором (`KBMediaAuthorizer`), а не доверием к HTML.
Публичный файл отдаётся только если он `scope=kb` и упомянут в `content_html`
публичного узла; отдельный `/api/public/kb/files/{id}` не вводился.
**Последствия.** Меньше поверхности XSS; проверка доступа — один SQL-запрос на
файл.

## ADR-11. Статистика: медиана и «в срок»

**Решение.** Время выполнения — `completed_at − created_at` (часы, округление
0.1, отрицательные → 0). Медиана: сортировка, нечётное — центральное значение,
чётное — среднее двух центральных, округление 0.1. `on_time_percent` — только
среди заявок с дедлайном; пустой набор → `null` у avg/median/on_time.
`total_done` — за всё время, остальные метрики — за период по `completed_at`.
**Последствия.** Метрики воспроизводимы в тестах; заявки без дедлайна не
занижают «в срок».

## ADR-12. Массовое перемещение: одна транзакция и порядок блокировок

**Контекст.** До 200 единиц; при параллельных операциях возможны deadlock.
**Решение.** `SELECT ... WHERE id IN (...) ORDER BY id FOR UPDATE` (единый
порядок блокировок), обновление и журнал в той же транзакции; отсутствующий id →
404 с откатом; единицы, уже находящиеся в целевом складе, пропускаются
(`skipped_count`), если все — 409. Репозиторий дополнительно сортирует и
дедуплицирует id.
**Последствия.** Нет частичных перемещений; 20 параллельных операций проверены
MySQL-тестом; блокировка держится на время записи журнала (до 200 строк).

## ADR-13. Контракт только аддитивно

**Решение.** `openapi/openapi.yaml` — источник истины; поля не переименовываются.
`skipped_count` добавлен аддитивно; `employees` не вводился (Б9 отдаёт `items`);
`deleted_by` не выдумывался — в `TrashItem` есть `deleted_by_user_id/name`.
**Последствия.** Сгенерированные типы фронта не ломаются; заглушки `501` — явный
признак нереализованной операции, а не пустой ответ.

## ADR-14. Демо-сид идемпотентен по маркерам

**Решение.** `api seed --demo` / `SEED_DEMO=true`; сущности ищутся по
детерминированным признакам (имя здания, логин, `DEMO-EQ-*`, `[демо]` в
описании, `Демо:` в заголовке БЗ). Настройки не перезаписываются, если строка
уже есть. Пароль демо-учёток — `SEED_DEMO_PASSWORD` (`Demo_12345`).
**Последствия.** Повторный запуск не плодит дубликаты; демо-данные можно
безопасно добавлять к рабочей базе (кроме пересечения логинов `demo.*`).

## ADR-15. Документы генерируются на сервере из тех же данных

**Контекст.** Word-заявка, Excel-статистика и ведомость должны содержать те же
данные, что JSON-эндпоинты, и подчиняться тем же правам.
**Решение.** `internal/documents` — тонкий слой поверх `tickets`, `stats`,
`equipment`: Word собирается по embed-шаблону `backend/templates/ticket.docx`
(замена плейсхолдеров в `word/document.xml`), Excel — из `stats.Service.ExportRows`
и списка единиц склада; второго SQL для тех же данных нет. Права и разбор
периода переиспользуют сервисы доменов; отдача — потоком с
`Content-Disposition: attachment` и `Cache-Control: no-store`.
**Последствия.** Один источник цифр для UI и документов; шаблон Word требует
перегенерации при изменении (`backend/scripts/gen-ticket-template.go`), формат
описан в `docs/templates.md`.

## ADR-16. Корзина: soft delete + 90 дней + ежедневная очистка

**Контекст.** Удалённые заявки/статьи/оборудование нужно восстанавливать, но
не хранить вечно.
**Решение.** Удаление пишет `deleted_at` и `deleted_by_user_id`, элемент
попадает в `GET /api/admin/trash`; восстановление сбрасывает `deleted_at`;
окончательное удаление (`purge`) удаляет строку и связанные медиа.
`trash.NewCleaner` запускается ежедневно в 03:00 по поясу приложения и убирает
элементы старше 90 дней (TRASH-4).
**Последствия.** Данные можно вернуть в течение 90 дней; физическое удаление
необратимо; списки «живых» сущностей обязаны фильтровать `deleted_at IS NULL`.

## ADR-17. Web Push без email/SMS

**Решение.** `webpush-go` + VAPID; без ключей транспорт в no-op (API работает,
подписки сохраняются). Outbox с backoff и `idempotency_key` для напоминаний.
**Последствия.** Нет внешних сервисов и затрат; push работает только при HTTPS и
поддержке браузера; iOS требует установленного PWA.
